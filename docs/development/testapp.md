# The Unity IL2CPP Test Application

`testapp/` is a minimal Unity 6 project whose only purpose is to give Mocha a
real IL2CPP player to load into. It is not a game and contains no Mocha
loader code; the loader is injected into its APK from outside.

## 1. What it is

| Item | Value |
|---|---|
| Unity | 6000.6.9f1 |
| Scripting backend | IL2CPP, Release |
| Architecture | `arm64-v8a` only |
| minSdk / targetSdk | 26 / auto (36 in the built APK) |
| Package | `dev.mocha.testapp` |
| Scene | `Assets/Scenes/MochaTest.unity` |
| Build output | `testapp/Build/mocha-testapp.apk` |
| Build flags | Development, AllowDebugging |

The scene is generated by `SceneBootstrap.CreateScene()` if missing: a camera,
a directional light, and a cube named `MochaTestCube` carrying
`TestBootstrap`. Nothing in the game calls Mocha; the loader reaches it through
the patched `libmain.so` and `il2cpp_init` (ADR 0001, 0002).

## 2. The managed surface under test

`Assets/Scripts/MochaTestTarget.cs` is a static class with `[Preserve]` on the
class and every member, so IL2CPP stripping (Low) cannot remove them:

| Member | Signature | Used to verify |
|---|---|---|
| `Add` | `static int Add(int a, int b)` | argument passing and int return through `runtime_invoke` |
| `Echo` | `static string Echo(string)` | managed string in/out |
| `Increment` | `static void Increment()` | call with no arguments and no return |
| `Info` | `static string Info()` | reading `Application.unityVersion` and `persistentDataPath` inside managed code |
| `Counter` | `static int Counter` | static field read/write across calls |
| `ThrowIfRequested` | `static string ThrowIfRequested(bool)` | present for exception-path experiments; not used by the shipped mods |

The native mods locate these by namespace, class, method name and arity:
`MochaTestApp.MochaTestTarget` in `Assembly-CSharp.dll`. They are deliberately
ordinary managed methods, not exported symbols; if IL2CPP name/arity lookup
works, the integration works.

`TestBootstrap` is a `MonoBehaviour` attached to the cube. It logs
`runtime-init`, `awake`, `start` and a heartbeat every 300 frames to both
logcat (`[MochaTest]`) and `Application.persistentDataPath/mocha-test.log`.
This is independent evidence that Unity reached the scene and is running after
the loader's early-startup window.

## 3. Why ARM64 only

Unity 6 removed the Android `x86_64` player architecture; requesting it
produces an ARM64-only APK. The project therefore sets
`PlayerSettings.Android.targetArchitectures = AndroidArchitecture.ARM64`, and
the x86_64 emulator runs it through the native bridge (Berberis /
`libndk_translation`). See `docs/testing/emulator-notes.md` §4. This is also
why the "same APK on a physical ARM64 device" claim is plausible but was not
tested on ARM64 hardware.

## 4. Building

From the repository root, with Unity 6000.6.9f1 and its Android module:

```
Unity -batchmode -nographics -projectPath testapp -buildTarget Android \
    -executeMethod MochaTestApp.Editor.BuildAndroid.Build -quit
```

`Assets/Editor/BuildAndroid.cs` configures the project every time (identifier,
minSdk, ARM64, IL2CPP, stripping, scene list), builds, logs a summary, and
exits 0/1. It requires a Unity license; in batch mode an unlicensed editor
fails before the build method runs.

The checked-in APK was produced this way. Rebuilding invalidates any
previously patched copy: re-run `tools/mocha_patch.py` after a rebuild.

## 5. Using it with Mocha

The full flow is in `docs/development/building.md` §3–§6. In short:

```
scripts/build_android.sh
python3 tools/mocha_patch.py --apk testapp/Build/mocha-testapp.apk \
    --out build/mocha-testapp-patched.apk \
    --shim build/android/native/libmain.so \
    --mocha build/android/native/libmocha.so
adb install -r build/mocha-testapp-patched.apk
```

Then push the example manifests and `.so` files to
`/sdcard/Android/data/dev.mocha.testapp/files/mocha/mods/` with app-UID
ownership (or use `scripts/run_emulator_test.sh`, which does it).

## 6. What the test app does not test

- Scene loading, gameplay, VR, input, rendering correctness, or performance.
  It is a launch target, and only startup ordering is observed.
- IL2CPP versions other than 6000.6.9f1. Changing the Unity version changes the
  player and requires a rebuild and re-test.
- Stripping levels other than Low. Higher stripping can remove the target
  methods despite `[Preserve]` if the class is otherwise unreferenced; the
  attributes are the safeguard, but this configuration was not re-tested.
- A release/non-debuggable or Play Store-signed build. The test APK is
  debuggable and debug-signed by the patcher.
- Shutdown. The app is force-stopped; the loader's unload path is not
  exercised.

## 7. Modifying the test target

If you add a method for a new test:

1. Add it to `MochaTestTarget` with `[Preserve]`.
2. Rebuild the APK (the generated `libil2cpp.so` changes).
3. Re-run the patcher.
4. Update the native mod that looks it up: the lookup is by name and
   parameter count; the return type is not part of the lookup.
5. Re-run L2/L3 and record a new artifact. Do not cite the old result for the
   new binary.

Changing the class or assembly name breaks the example mods by design; that
string is the contract the test exercises, and it lives in the mods, not in the
loader.
