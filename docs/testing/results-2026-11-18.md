### 3.6 Failure isolation

- `failing` was discovered, its manifest validated, its library loaded, and
  its entry called. Its return value 7 produced `failed:init` and
  `failing.result` with `called=true`, `return=7`.
- `hello` and `dependent` nevertheless loaded and ran afterwards.
- `missing-dep` was skipped before `dlopen`; its entry never ran and no result
  file was created.
- Unity continued startup to `InitializeScriptEngine OK`; the process did not
  crash on the failing mod.

A loader failure at the library level (`dlopen` failure, missing symbol) is
distinct from a mod returning non-zero; both are recorded per mod and do not
abort the loop in the tested cases. This run exercised `init` failure and
dependency skip; it did not exercise a `dlopen` failure at runtime (the
staging fallback succeeded for all three libraries).

## 4. L3 — real Unity IL2CPP

The player is Unity **6000.6.9f1**, IL2CPP, ARM64. `libil2cpp.so` exported
243 `il2cpp_*` symbols; Mocha resolves 27, of which 7 are required. All
required symbols resolved (`IL2CPP API resolved`, log line 801).

### 4.1 Domain and assemblies

- `il2cpp_init` returned domain pointer `0x1` (opaque handle; value is
  engine-assigned and not meaningful).
- `il2cpp_domain_get_assemblies` returned 19 assemblies at the point mods ran
  (line 802). This is the early-startup set, not the complete game catalog.
- Unity version was read as `6000.6.9f1` through the engine assembly and
  recorded in the summary and in `hello`'s output.

### 4.2 `hello.result`

```
ok=true
add=2+3=5
echo=echo:mocha
counter_before=0
counter_after=1
info=counter=1;unity=6000.6.9f1;persistent=/storage/emulated/0/Android/data/dev.mocha.testapp/files
```

This is `MochaTestTarget.Add(int,int)` returning 5, `Echo(string)` returning
the prefixed string, the static `Counter` field read before and after
`Increment()`, and `Info()` returning a string assembled inside managed code.
Each call went through `il2cpp_runtime_invoke` on the init thread.

### 4.3 `dependent.result` and ordering

```
ok=true
add=3+4=7
```

`dependent` requires `hello`, and the plan placed it after `hello`; it also
performs its own invoke (`Add(3,4)`) rather than reading a value produced by
`hello`. Its success therefore shows that a dependent mod can use the API
after the dependency loaded, but does not by itself prove the dependency's
initialization completed rather than merely its `dlopen`; the plan is
dependency-first and the loader runs entries in plan order (ADR 0003), which
is what the unit tests assert.

### 4.4 Timing

The mod work and the return to the engine are on the same thread, 23719, and
`CodeReloadManager initialized` / `InitializeScriptEngine OK` follow the
mods' completion (lines 826–828). This is the property ADR 0003 selected the
init-thread design for. It does not establish that all engine state was
ready; the domain and 19 assemblies were.

## 5. What passed and what would have failed

The harness treats these as failures: missing/incorrect summary, `loaded!=2`,
`failed!=1`, a `missing-dep` entry or result. None occurred.

The run would **not** have passed if:

- the shim had not been installed as `libmain.so` (no `JNI_OnLoad`, no gate);
- the gate had not been installed before `libunity`'s `JNI_OnLoad` (no
  `il2cpp_init` interception);
- staging had failed (all three `dlopen`s fail, `loaded=0`);
- the failing mod had aborted the loop (`dependent` absent);
- dependency resolution had loaded `missing-dep` (extra entry/result).

## 7. Validity limits

- **Not ARM64 hardware.** The emulator is x86_64 API 37 with
  `libndk_translation.so`; the arm64-v8a player runs under Berberis 16.0.0.
  Instruction translation can mask or introduce behavior differences
  (alignment, atomics, timing). L2/L3 conclusions are about the loader logic
  under this environment.
- **Not Quest (at the time of this run).** No Quest device was connected for
  the 2026-11-18 run, so Quest OS version, SELinux policy, linker namespace
  details, 16 KiB behavior on that kernel, and VR-specific startup behavior
  were not tested here. A later Quest 3 run is in
  `docs/testing/results-quest-2026-11-20.md`; this document's emulator
  conclusions are unchanged.
- **One Unity version.** 6000.6.9f1 only. The gate's ELF relocation handling
  and the IL2CPP export set were not exercised on another version.
- **Early startup only.** Mods ran during `il2cpp_init`, before scene load.
  No test covers calls after the first scene or the player loop.
- **No shutdown result.** `mocha_shutdown` exists and is called from the shim
  path, but this run did not capture `JNI_OnUnload`/shutdown behavior, so no
  runtime claim is made for it.
- **No adversarial mods.** No signature or integrity checks; a malicious or
  buggy native mod can crash or compromise the process. Not tested.
- **Single package/signer/layout.** No split APK, other signer, other ABI, or
  upgrade/uninstall scenario.
- **Static checks prove packaging, not execution.** `readelf`/`zipalign`
  success does not prove the device mapped the libraries the same way, though
  the run itself did install and execute them on 16 KiB pages.

## 9. Verdict

Within the stated limits: the loader builds, installs, starts before IL2CPP,
installs the gate in time, stages and loads native mods, resolves the IL2CPP
API on a real Unity IL2CPP player, invokes managed methods, isolates a
failing mod and a missing dependency, and reaches normal Unity startup. L1 and
the static packaging checks pass. **Quest compatibility was unverified at the
time of this emulator run;** it was later verified for the test player on a
Quest 3, as recorded in `docs/testing/results-quest-2026-11-20.md`.
